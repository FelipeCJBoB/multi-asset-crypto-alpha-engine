Arquitetura Motores quant Ago 2026

Núcleo funcional, casca imperativa

Por que um motor que treina e opera ao vivo sobre o mesmo código precisa separar a conta de quem executa a conta — e onde essa ideia já está publicada, com nome próprio, há mais de uma década.

00 O sintomaantes do nome

O bug que não é bug — é arquitetura.

Todo motor quant sério calcula a mesma coisa duas vezes: uma vez em lote, sobre o histórico inteiro, para treinar ou testar; e uma vez incremental, barra a barra, ao vivo. Se essas duas execuções são dois trechos de código diferentes — um script de treino de um lado, o motor de live do outro — elas vão divergir. Não é risco, é garantia estatística: dois textos independentes que deveriam computar a mesma fórmula sempre acabam computando fórmulas ligeiramente diferentes, cedo ou tarde, por causa de um ajuste que só foi feito num dos lados.

A correção não é revisão de código mais cuidadosa. É estrutural: existir só um lugar onde a conta é definida, e dois pontos de entrada que a chamam — nunca duas contas.

01 A arquiteturao desenho

Um pacote que não sabe rodar sozinho.

A regra: o código que calcula é 100% biblioteca — zero leitura de disco, zero rede, zero paralelismo, zero ponto de entrada. Recebe dado em memória, devolve dado em memória. Tudo que toca o mundo externo — CLI, iteração sobre o universo de ativos, paralelismo, persistência, relatório — vive numa casca fina, separada, um arquivo por etapa do pipeline.

core/
├── features/
│   └── volatility.py  # def compute(df) -> Series
├── labeling/
│   └── triple_barrier.py
└── models/
     └── ...
                  ↑ núcleo funcional — importável sem efeito colateral

scripts/
├── run_features_build.py  # --pairs --jobs --force
├── run_labeling.py
└── run_train.py
                  ↑ casca imperativa — CLI, I/O, paralelismo

O ponto de disciplina é o método duplo dentro do núcleo: a mesma conta ganha um método .batch(df) — usado pelo treino/backtest — e um método .streaming(buffer, novo_ponto) — usado pelo motor ao vivo. Um teste único afirma que os dois dão o mesmo número dentro de uma tolerância fixa. O runner de treino chama .batch(); o motor de live chama .streaming(); nenhum dos dois reimplementa a fórmula.

O sinal de que a arquitetura está certa: "a lógica está pronta" e "existe uma execução de produção que gerou este resultado" viram dois fatos que se pode checar separadamente. Sem essa separação, um módulo só pode estar tudo-ou-nada — e é exatamente aí que "testei localmente" vira, sem ninguém decidir isso, "está em produção".

02 Os quatro problemaso motivo, não o gosto

O que essa separação evita, concretamente.

1Testar sem I/O real

Lógica presa dentro de um script arrasta leitura de disco pra dentro de todo teste unitário. Lógica pura testa com um DataFrame sintético de 20 linhas em memória — milissegundos, não segundos, e sem depender de dado real existir.

2A mesma conta em dois mundos

O par .batch()/.streaming() com teste de paridade numérica é o que impede o motor de live de silenciosamente calcular uma coisa ligeiramente diferente do que foi validado no backtest.

3"Pronto" ≠ "em produção"

A separação cria um terceiro estado real: módulo implementado, testado, correto — e ainda sem runner porque ninguém rodou em escala. Isso precisa ficar visível em algum lugar, não implícito.

4Onde mora a evidência

"O algoritmo está certo" e "existe uma execução reproduzível que gerou este artefato" são fatos independentes. Só a separação permite representar os dois separadamente — e evita publicar um resultado de bancada como se fosse resultado de produção.

03 A literaturasim, tem nome

Isto não é invenção de projeto — tem três décadas de linhagem.

A pergunta tem resposta direta: sim, existe literatura publicada, em três camadas — engenharia de software geral, engenharia de ML especificamente, e um motor quant open-source que implementa exatamente este desenho como objetivo de projeto declarado.

2012 · Software design

Functional Core, Imperative Shell

Gary Bernhardt — Destroy All Software (screencast + talk "Boundaries", SCNA 2012)

O nome exato do padrão usado neste documento. Bernhardt descreve um núcleo que manipula só valores — sem tocar rede, disco ou stdin/stdout — cercado por uma casca fina que faz exatamente essas coisas, a partir dos valores que o núcleo produziu. O ganho citado é literal: o núcleo testa sem dublês de teste (test doubles), e a casca, por ter poucos condicionais, fica fácil de raciocinar sobre o estado ao longo do tempo.

termo de origem
destroyallsoftware.com/talks/boundaries · screencast
2005 · Software architecture

Hexagonal Architecture (Ports & Adapters)

Alistair Cockburn

Um padrão irmão, mais antigo e mais geral: isolar a lógica de domínio de toda infraestrutura (banco, API externa, fila) via interfaces (ports), com implementações concretas (adapters) do lado de fora. O núcleo de domínio não depende de infraestrutura nenhuma; as dependências apontam para dentro. É a formulação da mesma ideia em vocabulário de arquitetura corporativa, anterior ao termo de Bernhardt.

padrão irmão, mais amplo
alistair.cockburn.us/hexagonal-architecture
2015 · Machine learning, NeurIPS

Hidden Technical Debt in Machine Learning Systems

D. Sculley, G. Holt, D. Golovin et al. — Google, NeurIPS 2015

A formulação específica de ML do Problema 2 acima. O paper cataloga training-serving skew como um dos riscos sistêmicos de sistemas de ML em produção: a distribuição/representação usada no treino diverge da disponível em serving, e o sintoma clássico é métrica offline melhorando enquanto a métrica online estagna ou piora — o modelo foi treinado sobre uma distribuição que ele nunca vê em produção.

nomeia o Problema 2
papers.nips.cc/paper/5656

A prova de existência no domínio quant

NautilusTrader — motor de trading algorítmico open-source, Rust-nativo — declara este desenho como objetivo explícito de arquitetura: motor determinístico, orientado a eventos, onde a mesma implementação de estratégia, usando a mesma semântica de execução, roda inalterada da simulação para a produção. É o Problema 2 resolvido dentro do domínio exato deste documento — não engenharia de software genérica, motor quant de verdade, com a mesma tese: backtest e live compartilham o núcleo, nunca duas implementações.

nautilustrader.io · github.com/nautechsystems/nautilus_trader

04 Fecho

A convenção core/ puro + scripts/run_*.py como casca não é estilo pessoal de um projeto — é a aplicação de um padrão de 2012 (Bernhardt), sobre um problema catalogado em 2015 (Sculley et al.), que um motor quant real (NautilusTrader) já declara como o motivo de existir.

Isso é o que separa "convenção que copiei" de "engenharia que eu sei defender": a primeira pergunta que qualquer revisor sério vai fazer — "isso é padrão reconhecido ou gosto pessoal?" — já tem resposta, com nome e link.
